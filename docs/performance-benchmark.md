## 固定性能基准

在项目backend目录执行：

```bash
.venv/bin/python scripts/benchmark_performance.py --scenario warm --samples 12 --concurrency 4 --output logs/performance-latest.json
```

固定8种GET，每种12次，共96次；每轮结束后再开始下一轮，避免无界堆积。输出P50/P95/最大延迟、成功与错误数、压缩前后字节、后端进程CPU/RSS样本、代码指纹、数据版本与覆盖数量。

- `warm`：先预热一轮，再测量。
- `cold`：必须在新进程启动60秒内开始；该定义为启动后场景。证据读取本身会预热部分接口，不声称每次请求都是冷缓存。
- `background`：只有实际观察到扫描运行时才能测量，否则明确拒绝。工具不会为测试擅自启动全市场扫描。本轮未采集此场景样本。

其他应用和系统负载未被控制，报告中明确记录这一限制。应在相同代码、样本数、并发和场景下比较；不能将一次较低延迟当作稳定承诺。CPU为ps提供的进程统计，不是全机CPU，也不等同单个请求的CPU占用。

本机结果保存于backend/logs/performance-round3-*.json，已忽略，不上传Git。报告失败不会记为通过。

## 启动与重启

`start.sh`现在等待API、数据库和Redis真正就绪；端口监听或HTTP 200但状态为degraded均不足以判定成功。已注册后台服务时复用同一服务，避免额外启动第二个后端。

已安装的聚焦应用同步使用同一就绪检查，源启动脚本保存在scripts/app-launcher.sh。页面显示后台断连与自动重连状态，已有内容保留；连接恢复不意味着旧行情已被刷新，各指标仍以原时间为准。

显式部署重启：

```bash
bash scripts/restart-backend.sh
```

此入口捕获账本摘要、注销同一后台任务、等待旧进程退出、按原LaunchAgent配置重新注册，并确认新PID和依赖就绪，最后核对已有账本和流水。不会清空或恢复旧数据库。原服务的崩溃节流配置保留。

排查发现，API曾在启动时提前导入vectorbt回测依赖。现仅在回测调用时导入；异步回测的同步计算也移到线程中，原计算方法不变。前台导入样本从约3.174秒降至0.930秒；最后一次真实后台重启到就绪14.964秒，此前样本34.345、36.886、50.995秒。后台负载不同，该对比不作为固定时延保证。仍存在停机窗口，未实现零停机部署；首次回测仍有依赖加载与编译开销。

最后一次重启核验8份账本，已有建账信息、规则与成交历史一致，无新增成交。

## IOPV故障恢复

价格和IOPV必须来自同一响应及匹配的证券代码，不使用历史净值替代，不将空值当作0溢价。

- 主节点与一个东方财富备用节点，最多两次请求；这是同供应商冗余，不是独立来源核验。
- 超时、连接中断、限流、接口错误、代码不匹配和无效响应分别分类；遇429停止，不通过切换节点绕开限流。
- 整个基金分析等待IOPV最多7秒，失败时继续返回已有净值指标及可解释的未知状态。底层线程不能被asyncio强制终止，HTTP连接与读取另设超时。
- 成功时显示来源、供应商报价时间和采集时间；缺失或失败时显示中文提示，不生成估计值。

真实源本轮出现过一次成功和随后一次断开连接，说明外部可用性仍间歇波动。独立IOPV备用来源尚未核验，这部分仍列为待办。
